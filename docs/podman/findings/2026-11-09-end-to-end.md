# 2026-11-09: End-to-end test, manual install then Ansible

Question: do the manual guides still work as written after the move to `vm/vagrant/podman/`, `configs/podman/` and `docs/podman/`, and does the Ansible playbook build the same cluster? Open questions checked: the open questions on the [install_podman](../../../knowledge/okf/ansible/install-podman.md) knowledge page.

## Environment

- Host: 12 CPU threads, 38 GiB RAM, 113 GB free disk. Vagrant 2.4.9, VirtualBox 7.2.22r175245, box `cloud-image/ubuntu-26.04` 20260927.0.0, ansible-core 2.22.0.
- [Vagrantfile](../../../vm/vagrant/podman/Vagrantfile) with VirtualBox names `ceph-lab-podman-node-01` to `-03`.
- Ceph 20.2.5, cephadm and image pinned in [versions.yml](../../../configs/podman/versions.yml).
- No OS upgrade: the user dropped `apt-get upgrade`, `full-upgrade` and the reboot during this test. Every VM ran the box kernel `7.0.0-34-generic`.

## Procedure

1. `vagrant up`, then the [preflight](../diataxis/how-to/vm-preflight.md) on node-01 to node-03.
2. The first try at the OS upgrade was stopped by the user, the guide and Ansible were changed to skip it, and the three VMs were destroyed and recreated.
3. The [deployment guide](../diataxis/how-to/deploy-vm-cluster.md) and the [dashboard guide](../diataxis/how-to/dashboard.md) by hand, one command at a time over `vagrant ssh <node> -c '<command>'`.
4. `ansible-playbook site.yml` against the hand-built cluster.
5. `vagrant destroy -f`, `vagrant up`, then `ansible-playbook site.yml` on the new VMs, then a second run.

## Ansible on the hand-built cluster

`failed=0`. Changed: `apt-get update` on all three VMs, and the two layout files with their `ceph orch apply` on node-01, because the generated files differ from the uploaded ones in their header comment. No bootstrap, no disk change, no certificate or user change. Afterwards `HEALTH_OK`, 3 OSDs, `/dev/sdc` still available. `cache_valid_time: 3600` was added so a rerun does not report the package refresh as a change.

## Ansible on new VMs

| Run | Result | Cause and fix |
| --- | --- | --- |
| Straight after `vagrant up` | `UNREACHABLE` on all three: `ssh: connect to host 192.168.56.11 port 22: Connection timed out`; nothing changed | The VMs did not answer SSH on the host-only address yet. `ansible ceph -m ping` worked a minute later. `ansible.cfg` now has `timeout = 30` and SSH `retries = 5` |
| Second try | bootstrapped, then `UNREACHABLE` on the delegated SSH key task: `vagrant@192.168.56.12: Permission denied (publickey)` | The SSH key path used `inventory_hostname`, which keeps the name of the original host under `delegate_to`, so node-01's key was offered to node-02. Each host now has `vagrant_machine` in `hosts.yml`, and the key path uses it, as in kube-lab |
| Third try, same VMs | `failed=0`; node-01 `changed=25`, node-02 and node-03 `changed=0`; bootstrap skipped (`ok`), key added on both VMs, `HEALTH_OK`, 3 MONs, 3 MGRs, 3 OSDs | Resuming after a failure works |

Checked afterwards from the host and node-01: every service at its full count, `CN=ceph-lab-gateway` on each address, dashboard `200`, `/dev/sdc` `Available Yes` on all three, `/root/ceph-dashboard-password` `-rw------- root` 32 bytes. The monitoring wait now uses `ceph orch ls <service> --refresh` for the stale-list reason above.

A second full run on the finished cluster gave `failed=0` and `changed=0` on node-01, node-02 and node-03.

## Result

The manual guides build the cluster as written, with three corrections: the package install output without an OS upgrade, `--refresh` for the service list, and a short wait after the gateway restart. The Ansible playbook builds the same cluster on new VMs after two fixes: per-host SSH keys under `delegate_to`, and SSH retries for VMs that have just booted. No disk was wiped, and no OSD was created with `--all-available-devices`.

## Limitations

The dashboard was not opened in a browser and the first login was not done. The reserve disk exercise, the client VMs and the snap method were not part of this test.
